# LogicBox

LogicBox checks the logical structure of a paper without pretending to decide
whether its claims are factually true.

Shen is the reasoning engine. Python only launches Shen, preserves artifacts,
records hashes and traces, and creates immutable run directories.

## What You Can Do Today

The current release is a command-line reasoning engine. It does not yet include
a text editor or a built-in OpenAI/OpenRouter connection.

To review a paper today:

1. Write or paste the paper into a text file.
2. Use an AI model to translate the paper into a LogicBox `source.shen`
   artifact.
3. Run LogicBox to validate and analyze that artifact.
4. Give the paper and Shen findings to an AI model for explanation or revision.
5. Re-extract and re-run the revised paper.

The AI handles language. Shen handles logical validation and inference.

## Install

Requirements:

- Python 3.11 or newer
- a Shen/SBCL batch executable that accepts ordered `-l FILE` arguments

Install LogicBox from the repository:

```sh
git clone https://github.com/juangrukat/logicbox.git
cd logicbox
python3 -m venv .venv
. .venv/bin/activate
python -m pip install .
```

Configure the Shen executable:

```sh
export SHEN_SBCL=/absolute/path/to/shen-sbcl
logicbox doctor
```

A working installation prints:

```text
shen.runtime	ok	/absolute/path/to/shen-sbcl
```

LogicBox packages its Shen source files, but it does not bundle the Shen/SBCL
runtime itself.

## Check A Paper

The following is the recommended end-to-end workflow.

### 1. Create A Review Directory

```sh
mkdir -p paper-review/runs
cp /path/to/your-paper.txt paper-review/paper.txt
```

Plain text works best. Convert `.docx` or PDF files to text before extraction.

### 2. Generate The Current AI Contract

```sh
logicbox contract --output paper-review/contract.shen
```

This file is generated by Shen from the current schema. It tells the AI which
facts, identifiers, and controlled values it may use.

### 3. Ask An AI To Extract The Paper

Give the AI these files:

- `paper-review/paper.txt`
- `paper-review/contract.shen`
- [`docs/prompt-contract.md`](docs/prompt-contract.md)

Use a prompt like this:

```text
Translate the attached paper into one complete LogicBox source artifact.

Follow contract.shen and docs/prompt-contract.md exactly.
Represent only claims actually present in the paper.
Preserve uncertainty and unresolved assumptions.
Do not add evidence, mechanisms, definitions, or conclusions.
Do not emit Markdown or commentary.
Return only the complete Shen artifact beginning with:
(set *logicbox-artifact* ...)
```

Save the AI response unchanged as:

```text
paper-review/source.shen
```

Do not convert it to JSON or edit its logical structure with Python,
JavaScript, regular expressions, or another serializer.

### 4. Run The Review

```sh
RUN_DIR=$(
  logicbox run \
    --input paper-review/source.shen \
    --run-dir paper-review/runs
)

printf '%s\n' "$RUN_DIR"
```

LogicBox prints the immutable run directory. A successful run contains:

```text
input/source.shen
schema/accepted.shen
schema/diagnostics.shen
analysis/findings.shen
schema/engine.stdout
schema/engine.stderr
analysis/engine.stdout
analysis/engine.stderr
manifest.json
```

### 5. Understand The Review Folder

The review folder is an audit bundle. It preserves what was submitted, what
Shen accepted, what Shen found, and how the run was executed.

It is not yet a polished human-readable report. The current release produces
machine-oriented Shen artifacts. An AI or a future LogicBox interface must
translate those findings into prose.

A folder such as:

```text
validity-test-review/
├── paper.txt
├── source.shen
└── run/
    ├── input/
    │   └── source.shen
    ├── schema/
    │   ├── accepted.shen
    │   ├── diagnostics.shen
    │   ├── engine.stdout
    │   └── engine.stderr
    ├── analysis/
    │   ├── findings.shen
    │   ├── engine.stdout
    │   └── engine.stderr
    └── manifest.json
```

should be read in this order:

1. `paper.txt`: the original paper.
2. `source.shen`: the AI's logical extraction of the paper.
3. `run/schema/diagnostics.shen`: whether the extraction was valid.
4. `run/analysis/findings.shen`: the structural issues Shen derived.
5. `run/schema/accepted.shen`: the exact facts Shen accepted.
6. `run/manifest.json`: hashes, file sizes, timing, and runtime information.
7. `engine.stdout` and `engine.stderr`: debugging traces, usually not needed.

`source.shen` and `run/input/source.shen` should contain the same artifact. The
copy inside `run/input/` is frozen as part of the immutable run.

#### How To Read Diagnostics

The important part is the artifact's `payload`.

```shen
[kind diagnostics]
[payload []]
```

An empty diagnostics payload means the extraction passed the Shen schema gate.
It does not mean that the paper is logically sound. It means Shen could
understand the submitted facts well enough to analyze them.

A nonempty diagnostics payload may contain entries such as:

```shen
[fact-type-error ...]
[fact-warning ...]
[fact-suggestion ...]
```

These usually indicate a problem in the AI extraction or artifact format.
Correct the extraction before interpreting the paper's logical findings.

#### How To Read Findings

`findings.shen` contains the conclusions produced by the rules engine. For
example:

```shen
[missing-mechanism c2]
[unclear-scope c3]
[context-conflict ctx-lid-absent ctx-lid-present]
[conclusion-stronger-than-ground g1 k1 possible certain]
[stage-chain-too-short c1 2 3]
[missing-stage-bridge c1 s1 s2]
[scope-conflict f-global-handle f-local-handle global local]
[plan-status p1 needs-user-input]
```

These mean:

- `missing-mechanism c2`: claim `c2` states a causal relationship but does not
  explain how the cause produces the result.
- `unclear-scope c3`: claim `c3` does not say clearly when or where it applies.
- `context-conflict A B`: the extraction treats two incompatible conditions as
  simultaneously known.
- `conclusion-stronger-than-ground`: the conclusion is stated more certainly
  than its supporting ground permits.
- `stage-chain-too-short`: the proposed causal explanation has fewer
  intermediate stages than it claims to require.
- `missing-stage-bridge`: two adjacent stages are listed without an explanation
  connecting them.
- `scope-conflict`: the same concept is used under incompatible scopes.
- `plan-status ... needs-user-input`: unresolved structural questions remain.

IDs such as `c2`, `g1`, and `k1` refer back to facts in `source.shen` and
`accepted.shen`. For example:

```shen
[claim c2 causal furniture-watching sugar-dissolving]
```

allows `[missing-mechanism c2]` to be read as:

> The paper says furniture watching causes sugar to dissolve, but it does not
> supply a mechanism connecting those events.

#### Example: `validity-test-review`

The test of `validity-test.txt` produced:

```shen
[payload []]
```

in `schema/diagnostics.shen`, so the extraction was valid.

Its `analysis/findings.shen` reported:

- missing mechanisms for furniture watching causing sugar to dissolve and for
  suspicion causing ownership;
- unclear scope for the ownership claim;
- conflicts between yesterday having happened and not having happened;
- conflicts between the lid being absent and present;
- conflicts between public and private ownership;
- a conclusion stated as certain despite only possible support;
- a causal chain with too few stages and no bridge;
- incompatible global and local descriptions of the handle.

The final status was `needs-user-input`. In an ordinary paper this means the
writer or reviewer must clarify the unresolved claims. In this deliberately
absurd test, the findings show that Shen preserved and detected the intended
paradoxes rather than silently making them coherent.

### 6. Read The Results

Inspect the operational record:

```sh
logicbox inspect --run-dir "$RUN_DIR"
```

Read the Shen artifacts:

```sh
cat "$RUN_DIR/schema/diagnostics.shen"
cat "$RUN_DIR/analysis/findings.shen"
```

The files mean:

- `accepted.shen`: facts Shen accepted for reasoning.
- `diagnostics.shen`: malformed facts, type errors, warnings, and suggestions.
- `findings.shen`: structural issues inferred by the Shen rules engine.
- `engine.stdout` and `engine.stderr`: exact process traces for diagnosis.
- `manifest.json`: paths, hashes, sizes, timing, and exit status only.

For normal use, begin with `diagnostics.shen` and `findings.shen`. Open
`accepted.shen`, `manifest.json`, or the engine traces only when you need to
audit or diagnose the run.

Common findings identify missing context, unsupported conclusions, unclear
scope, missing causal stages, unresolved objections, inconsistent modality, or
unsafe rewrite mutations.

If diagnostics report a translation error, correct the AI extraction and run
LogicBox again. Do not rewrite the paper merely to hide a bad extraction.

### 7. Ask An AI To Explain Or Revise The Paper

Give the AI:

- the original `paper.txt`
- `schema/diagnostics.shen`
- `analysis/findings.shen`

For an explanation, use:

```text
Explain each Shen diagnostic and finding in plain language.
Tie every explanation to the exact passage in the attached paper.
Separate extraction problems from genuine structural gaps.
Do not decide whether the paper's factual claims are true.
Do not invent evidence or missing premises.
```

For a whole-paper revision, use:

```text
Revise the entire attached paper using the Shen diagnostics and findings.

Preserve the author's claims, modality, scope, conditions, objections,
exceptions, and uncertainty.
Improve organization and clarity.
Do not invent facts, evidence, dates, statistics, mechanisms, or citations.
Where a finding cannot be resolved from the paper, leave a clear bracketed
placeholder or editorial question.

Return the complete revised paper, not a summary and not Shen facts.
```

Save the result as:

```text
paper-review/revised-paper.txt
```

### 8. Recheck The Revision

Repeat the extraction step using `revised-paper.txt`, saving the new artifact as
`revised-source.shen`, then run:

```sh
REVISED_RUN_DIR=$(
  logicbox run \
    --input paper-review/revised-source.shen \
    --run-dir paper-review/runs
)

logicbox inspect --run-dir "$REVISED_RUN_DIR"
cat "$REVISED_RUN_DIR/analysis/findings.shen"
```

Keep both run directories. Their manifests and exact artifacts make the review
traceable and reproducible.

## Low-Level Commands

Run the schema stages without creating a complete run:

```sh
logicbox schema \
  --input source.shen \
  --accepted accepted.shen \
  --diagnostics diagnostics.shen
```

Analyze accepted facts:

```sh
logicbox analyze --input accepted.shen --output findings.shen
```

Compare accepted source and structured rewrite-candidate artifacts:

```sh
logicbox compare \
  --source accepted.shen \
  --candidate candidate.shen \
  --output mutation.shen
```

`compare` is an advanced logical-artifact operation. It does not compare two
plain-text papers.

Commands refuse to overwrite outputs unless `--replace` is supplied. Add
`--trace` to send stage timing and exact Shen stdout/stderr to stderr.

## Architectural Boundary

`.shen` files are the sole logical interchange format. Only Shen may read,
validate, normalize, transform, or emit their logical payloads.

Python treats `.shen` files as opaque bytes. JSON manifests contain operational
metadata only and never contain facts, findings, or translated payloads.

## Verify The Installation

Run a bundled stress artifact:

```sh
logicbox run \
  --input tests/artifacts/stress-policy-graph.shen \
  --run-dir /tmp/logicbox-runs
```

Run the complete test suite:

```sh
python -m pip install '.[test]'
SHEN_SBCL="$SHEN_SBCL" python -m pytest -q
```

The suite includes schema failures, mutation safety, concurrency behavior,
immutable-run checks, exact behavioral parity, and demanding multi-rule Shen
stress cases.

Natural-language stress papers and their authoritative extracted artifacts live
in:

```text
tests/texts/
tests/artifacts/
```
